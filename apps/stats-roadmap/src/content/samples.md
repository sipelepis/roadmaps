# Thinking in samples

Every number in statistics comes from a sample. Flip seeded coins, watch a proportion settle, and decide what close enough means.

## Seeded randomness

A computer cannot flip a coin, so it runs a recipe that produces numbers that look random. The recipe starts from a number called the seed. The same seed always gives the same sequence.

```python
import random

rng = random.Random(1)
print(rng.random())
print(rng.random())
print(random.Random(1).random())
```

This prints `0.13436424411240122`, then `0.8474337369372327`, then `0.13436424411240122` again. `random.Random(1)` builds a generator, and we call it `rng`. Each `rng.random()` returns a float in `[0, 1)`: at least 0, always below 1. A new generator with the same seed starts the sequence over.

A coin that lands heads with probability `p` is one comparison:

```python
heads = rng.random() < 0.3
```

`rng.random()` is below 0.3 about 30% of the time, so `heads` is `True` about 30% of the time. Count `True` as 1 and you have a 0/1 outcome.

Pass `rng` into every function that needs randomness instead of reaching for the module-level random functions. Then the caller decides the seed, a test can pin the exact answer, and two functions never steal each other's draws. Python promises that `rng.random()` gives the same sequence for the same seed on every version, which is why the tests on this roadmap can hard-code exact values built from it.

## Samples and populations

The population is everything you care about: every visitor next month, every request your service will ever see. The sample is the part you actually looked at. You never see the population. You see a sample and compute a statistic from it, such as a proportion, and that statistic is an estimate of the population value.

An estimate moves when the sample moves. Here the true heads rate is 0.3, and each seed is a different sample of 100 flips:

```python
for seed in range(5):
    rng = random.Random(seed)
    print(seed, sum(rng.random() < 0.3 for _ in range(100)) / 100)
```

The five estimates are `0.18`, `0.27`, `0.23`, `0.25` and `0.34`. None is wrong, none is exactly 0.3, and no single one tells you how far off it is. Most of statistics is about saying how far off an estimate can be.

## Running proportions

Take one long sequence of flips and compute the proportion of heads after each flip. Early on it wanders. Later it settles near the truth.

```python
xs = [1 if rng.random() < 0.3 else 0 for _ in range(10000)]
print(sum(xs[:10]) / 10)
```

With `random.Random(5)` and `p = 0.3`, the proportion after 10, 100, 1,000 and 10,000 flips is `0.1`, `0.34`, `0.312` and `0.2995`. The distance from 0.3 is `0.2`, `0.04`, `0.012` and `0.0005`. Each time the sample gets 10 times bigger, the error is a few times smaller, not 10 times smaller.

The error shrinks roughly like `1 / sqrt(n)`, where `n` is the number of flips. That is `0.3162`, `0.1`, `0.0316` and `0.01` for the same four sizes. It is a rule of thumb here, and the module [Large numbers & the CLT](#/clt) makes it precise. For now: to halve your error you need four times the data.

## Close enough

You will compare an estimate with a truth all through this roadmap, so name the two ways to do it.

```
absolute error = |estimate - truth|
relative error = |estimate - truth| / |truth|
```

An estimate of 0.34 for a truth of 0.3 is off by `0.04` in absolute terms and by `0.133333333` relatively, rounded to nine places. Relative error says how big the miss is compared with the thing you measure, so it makes 1,003 against 1,000 and 0.0003 against 0.0002 comparable. It is undefined when the truth is 0, because you would divide by zero. A function that computes it should raise `ValueError` there and say why.

Floats are not exact. `0.1 + 0.2` is `0.30000000000000004`, so `0.1 + 0.2 == 0.3` is `False`. Never compare computed floats with `==`. The standard library has `math.isclose(a, b, rel_tol=..., abs_tol=...)` for this. It treats `a` and `b` symmetrically: the tolerance is `rel_tol` times the larger of the two. Its default `abs_tol` is 0, so `math.isclose(0.0, 1e-12)` is `False` and `math.isclose(0.0, 1e-12, abs_tol=1e-9)` is `True`. Anything compared against 0 needs an absolute tolerance.

The `close_enough` function you write below is relative to the truth instead, which is the question you ask about an estimate: is it within 1% of the real value? The two differ only in a thin band. With a truth of 1000 and an estimate of 1010.05, the error is 10.05, which is above 1% of 1000, but `math.isclose(1010.05, 1000, rel_tol=0.01)` is `True` because it measures 1% of the larger number.

The tests on this roadmap follow the same rule. They round a float to nine places before comparing it, as in `round(got, 9) == 0.033333333`, and for lists they round each item. See [How the tests work](#/reference/how-the-tests-work).

```python playground
import math
import random


def flips(n, p, rng):
    return [1 if rng.random() < p else 0 for _ in range(n)]


rng = random.Random(5)
xs = flips(10000, 0.3, rng)
for n in (10, 100, 1000, 10000):
    est = sum(xs[:n]) / n
    print(n, est, round(abs(est - 0.3), 4), round(1 / math.sqrt(n), 4))

# Try: change the seed, or p, and see which sizes settle first.
print(0.1 + 0.2 == 0.3, math.isclose(0.1 + 0.2, 0.3))
```

def test_errors():
    """absolute and relative error"""
    assert round(abs_error(0.34, 0.3), 9) == 0.04
    assert round(rel_error(0.29, 0.3), 9) == 0.033333333
    assert round(rel_error(-8.0, -10.0), 9) == 0.2


def test_zero_truth():
    """relative error against a truth of 0 raises ValueError"""
    try:
        rel_error(0.5, 0)
    except ValueError:
        pass
    else:
        raise AssertionError('a truth of 0 should have raised ValueError')


def test_close_enough():
    """within a relative tolerance of the truth"""
    assert close_enough(1003, 1000) is True
    assert close_enough(1020, 1000) is False
    assert close_enough(1010.05, 1000) is False
    assert close_enough(0.29, 0.3, rel_tol=0.05) is True


def test_abs_tol():
    """a small truth needs an absolute tolerance"""
    assert close_enough(0.0003, 0.0002) is False
    assert close_enough(0.0003, 0.0002, abs_tol=0.001) is True
    assert close_enough(0.0005, 0) is False
    assert close_enough(0.0005, 0, abs_tol=0.001) is True
